# Existing remote verifier for later operator candidates

The current four candidates are already under local checks and should finish those runs. For later new candidates, RUNBOOK.md documents four existing remote verification slots and the ordinary `factory-ng-verify-remote.py` transport. It enforces pinned proposal/ticket/source identities, per-ticket scope, registration checks, every original gate, and source-tree integrity, then imports immutable accepted receipts. It may be usable directly for one operator correction at a time without a provider run or live-job mutation. This has been inspected, not yet exercised for operator candidates.

Relevant API: `factory_ng_verification.save_proposal(directory, clone, ticket_path, identity, context)` stages the isolated clone and writes a hash-bound untested proposal. Identity requires worker/model/profile. Use truthful operator identity and zero model-call telemetry. Manifest entries require ticket_id, ticket_path, proposal, and identity. Remote CLI accepts --manifest and --slot. Host supervisors serialize slots. Actual remote gate failures remain failed and must not be hidden by an unchanged retry. A valid returned accepted receipt already contains a format-patch artifact and can go through the normal operator integration wrapper with the operator ticket parents; it does not need to be recreated by accept-operator.py. Inspect the preparation contract and current slot availability before using it. Never submit an in-progress or changing clone.
