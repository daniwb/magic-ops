A from-scratch Magic: The Gathering rules engine written in Go. About 12,400 cards are implemented across two pipelines that both register into one small, event-driven core.

01Two ways a card reaches the engine

Everything below is read out of the actual source in backend/game, backend/cards and backend/cardfns as of this snapshot.

The “handler wins” rule. There is exactly one precedence switch per card class. For a permanent, the switch is RegisterCardAbilities on every battlefield entry: if CardHandlers[name] exists, it runs and the DSL path is skipped. For an instant/sorcery, the switch is spell resolution: if SpellHandlers[name] exists, it runs the whole effect instead of interpreting card.SpellEffect.

Beyond those two maps

cardhandlers.go holds a family of name-keyed registries for behaviour that has to exist before a card is ever cast — a permanent's ETB handler is too late: CastRestrictions, CostReductionFns, ColoredCostReductionFns, DynamicSpellCostReductionFns, EquipCostReductionFns, IntrinsicExilePlayFns, OpeningHandHandlers — all populated from cardfns init() functions.

02One game loop, three reaction mechanisms

Everything that happens in a game funnels through the same shape, whichever pipeline produced it.

03Deep dive — a triggered draw

Example: Mulldrifter, “When this creature enters, draw two cards.”

Runtime step by step: the spell resolves and RegisterCardAbilities subscribes the ability → the engine publishes CreateETBEvent → EventBus.Publish matches it against every registered condition (after consulting trigger-suppression statics) and returns the match rather than running it → it's wrapped in a StackObject and waits on the stack (Rule 603.3) → on resolution, ExecuteAbilityEffect dispatches case "draw" → DrawCardWithEvent, the single draw chokepoint, which checks ReplacementManager.GetDrawReplacement before moving any card.

04Deep dive — casting a spell and resolving the stack

The busiest chokepoint in the engine — nearly every registry above gets consulted here.
